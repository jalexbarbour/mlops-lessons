lora-hparam-sweep

A grid search over LoRA rank and learning rate for the same toy task as mlx-finetune-lab — every config logged as its own MLflow run, every resulting adapter scored on the same held-out test set. The question isn't whether fine-tuning works, it's which config wins, and how you'd know.

Why rank val_loss and test accuracy separately

val_loss is what the optimizer sees during training and is cheap to compute every few steps — useful for catching divergence early, as it does here for every lr=3e-4 run. It is not the same question as "does the fine-tuned model actually produce the right JSON on inputs it hasn't seen," which only a held-out generation-based eval answers. compare.py computes both and logs them onto the same MLflow run, so a config's training curve and its real-world accuracy live side by side instead of requiring two separate lookups.

Pipeline

  1. Install dependencies

    uv sync

  2. Generate the dataset

    Same generator as mlx-finetune-lab, copied for self-containment — deterministic, seeded.

    uv run python data/generate_dataset.py

  3. Run the sweep

    9 configs (rank × learning rate), each a fresh model load and its own MLflow run under the *-sweep experiment.

    uv run python sweep.py

  4. Evaluate and rank

    Scores every adapter on the held-out test set, logs test_exact_match / test_field_accuracy back onto each run, prints the ranked leaderboard.

    uv run python compare.py

Inspect experiment tracking

uv run mlflow ui --backend-store-uri sqlite:///mlflow.db

Repository layout

data/generate_dataset.py — same toy-task generator as mlx-finetune-lab
sweep.py — grid search, one MLflow run per (rank, learning_rate) pair
compare.py — test-set evaluation + ranked leaderboard across all sweep runs
adapters/, mlruns/, mlflow.db — generated, gitignored
